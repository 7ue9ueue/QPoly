## Findings

- Zen 3 parser: the per-stream scan chain is ~60% of the step, but halving it (ms4) gains little; the
  conversion alone (0.83 ns/token) is close to the step's cost, and pipelining the two in C++ made GCC's
  code much slower. Without hardware counters the remaining bottleneck is not identified.
- Zen 3 formatter: not instruction-bound (76 vs ~97 instructions per 8 values: same speed); stores
  matter (four 32-byte stores instead of eight 16-byte ones: −1.5 ms micro, −4 ms e2e output phase).
- Code layout: two builds with identical formatter instructions differed by 11 ms of user time on one
  host (asm grouping 2 vs 4 blocks per statement); the 2-block grouping was consistently better across
  hosts. Decisions used several hosts and in-process phases (`launcher_opt.c` parses probe lines).
- NTT: the bottom stage's scalar inputs are not on its critical path (lookahead neutral/worse); generating
  twiddles on the fly costs ~42 scalar multiplies per group and is throughput-bound (+5%).

## Validation

- Formatters: asm (`block8`, `blocks<2/4>`, four-store `block8_s4`, `blocks2_s4`) equal `blocks3` for every
  value < 10^9 (exhaustive, locally under Rosetta and in CI natively), 2M random 32-value groups, edges.
- Parsers: `bench_opt unit` (2,758 runs: random, 9-digit, 1-digit, uniform-length, edges, 40 short streams,
  single spaces and mixed whitespace (fallback), resumed calls, fixed-width round trips), ASan/UBSan.
- Transform variants (N1, lookahead): bit-identical to `qlarge::Core` for lg 9–25, generator equal to the
  root tables entry by entry, Core checked against a textbook NTT (lg ≤ 18) / 8 random points.
- Programs: byte-identical to the exploration-011 deliverable on 13 local inputs (1×1 … 2^24×2^24, the
  2^24 branch, 2^24×1000, 1–97-value outputs, CR LF/tab/double-space input) plus the independent 8-point
  checker; every e2e run compares every output with the hash-verified model output (token-equal).
- Official (round 11, `work/ntt/conv_large/run_official_all.sh`): all 54 cases generated with the official
  generators and seeds (inputs hash-checked), judge flags and container limits; the exploration-010
  deliverable (`ref010`) byte-exact against hash.json on all 54; the final file and its probe twin
  byte-exact on 11 and accepted by the problem's checker (testlib wcmp) on 43 — 162 runs, 0 failures.
- Untested: the real judge; THP `never`; Intel judge hardware (the asm formatter is ~4% slower than
  GCC's code on Zen 4/5 in micro, though e2e still gains there).
