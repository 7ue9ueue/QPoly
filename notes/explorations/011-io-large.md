## Research

- Checker: testlib `wcmp` (problem's checker.cpp at library-checker-problems 1814c4e5) compares
  whitespace-separated tokens as strings; output limit 512 MiB. A fixed 10-byte field per value
  (9 right-aligned characters, space padded, one separator) prints canonical tokens (no leading
  zeros) and is accepted: 335,544,320 bytes at 2^25 values vs 331.2 MB for variable width (+1.3%,
  ~1.6 ms of write()).
- Input format: the problem's [verifier](https://github.com/yosupo06/library-checker-problems/blob/1814c4e5205517e368bb57a8d1127eb961cfeaae/convolution/convolution_mod_large/verifier.cpp)
  requires exactly one space between values and one `\n` per line (testlib `readInt`, `readSpace`,
  `readChar('\n')`), so a parser may assume one separator per token on its fast path and fall back
  to a general parser otherwise.
- Digit conversion with `pmaddubsw`/`pmaddwd` chains is standard (e.g.
  [kholdstare 2020](https://kholdstare.github.io/technical/2020/05/26/faster-integer-parsing.html));
  table-driven SIMD parsing of integer series: [W. Muła, parsing-int-series](https://github.com/WojciechMula/parsing-int-series)
  (pattern tables indexed by separator masks; not used: tables for 10-byte tokens are large).
- Integer to string: [Champagne Gareau & Lemire 2026](https://arxiv.org/abs/2604.26019) reach
  0.73 ns/value for 8-digit values with AVX-512 IFMA on Zen 5 (not available on Zen 3); the
  SWAR digit-pair splitting used below (x + (x/100)·(2^16 − 100), then per half ·(2^8 − 10)) is the
  usual itoa trick applied to 32-bit lanes.
- Breaking a serial decode chain by interleaving independent streams is the idea behind e.g. the
  four-stream Huffman decoders of zstd; here the "streams" are sub-chunks cut at token boundaries.

## Parser (rounds 1–2, 4–7)

The 007 parser (`qp_parse_flat`) first extracts separator positions for 2 KiB (8 unconditional
tzcnt/blsr extractions per 64 bytes), then parses four tokens per step from the positions.

| Variant (2^25 random residues) | EPYC 7763 ms |
| --- | --- |
| per-token SSE (judge 406478) | 112.0–112.5 |
| `qp_parse_flat` (007, deliverable of 010) | 68.1–69.3 |
| `tail`: windows ending at separators, guarded input | 70.6–71.8 |
| `tail8`: 8-token steps | 73.4–73.5 |
| `ms` K = 4 streams, one token per stream step, 32 KiB chunks | 58.9–60.1 |
| `ms` K = 8 (register spills) | 74.7–75.8 (16/64 KiB chunks 78.8–80.2 / 72.3–73.0) |
| **`ms2`: 4 streams × 2 tokens per step (one 32-byte load/compare/movemask per two tokens)** | 16 KiB 52.8–54.8, 32 KiB 48.6–51.5, 64 KiB 47.1–48.8, **128 KiB 46.5–46.9** |

`ms2` details: a chunk is cut into four sub-chunks at token boundaries (`snap`); each stream step
loads 32 bytes, takes the first two separators (tzcnt, blsr, tzcnt), inserts the second token's
16-byte window next to the first and right-aligns both with one length-indexed `vpshufb`; the
reduction (maddubs, madd, packus, madd, shufps split, mullo 10^8) yields eight values per step,
stored as two consecutive values per stream (stream 0 directly into the destination, others into
static regions copied after the chunk). No per-token bounds checks: a step advances ≤ 33 bytes
whatever the input, so `min(bytes left) / 33` steps run unchecked, repeated, then single-token
drains. Validation is vector-only: lengths outside 1..16 select a shuffle row whose byte 15 is
negative; the rows are ORed and checked once per chunk with the stream end positions; a flagged
chunk is re-parsed by `qp_parse_flat` (so double spaces, CR LF and tabs stay correct, only slower).
Per-chunk overhead ≈ 0.34 µs (from the chunk-size series), so 128 KiB chunks.

`ms3` (round 7: controls from an 80-byte sliding ramp instead of 16-byte rows, 64-bit scans with
bits 31..63 preset, 93 instead of ~110 instructions per 8 tokens in GCC's loop; K = 8 as two groups):
no gain on AMD (9V74: 43.1 vs ms2 42.9 ms, K = 8 46.3–48.9; e2e 7763 457.6 vs 455.8), better on
Intel 8573C (47.7–53.9 vs 51.0–57.2). Kept as a variant; ms2 is the deliverable's parser.

## Validation

- Formatters: every value < 10^9 against the scalar reference (CI `bench_io_large unit` each round,
  and locally), random/dense blocks for G = 2, 4, edge values; round trip through the parsers.
- Parsers: 3,088 runs locally under ASan/UBSan (random, 9-digit, single-digit, uniform-length
  (imbalanced sub-chunks), edge values, 40 short streams, mixed whitespace, resumed calls) and in CI.
- Programs: local (Rosetta) byte/checker comparison on 7 inputs up to 2^23 tokens, a pipe input, and
  13 adversarial inputs (CR LF, tabs, double spaces, imbalanced digit lengths, all zeros, P − 1,
  chunk-threshold sizes, and output counts that are multiples of 16384) against the
  exploration-007 outputs (testlib wcmp) or an independent 8-point evaluation checker.
- Official: all 54 cases in rounds 1 (`eight()` + tail parser + guarded input) and 8 (deliverable
  and probe: 162 runs, 0 failures; 11 byte-identical, 43 accepted by the problem's wcmp checker
  against the 010 deliverable's outputs, which match hash.json). The verified sources are in
  [results/io-large/36322772709/conv-large-official](../results/io-large/36322772709/conv-large-official/).
- CI unit job (round 8, 3 × EPYC): all formatters equal the reference for every value < 10^9.
- Bug found and fixed before round 8: builds of rounds 1–7 flushed the output buffer after a block,
  so when the last block ended exactly at the buffer end (count a multiple of 16384 with a 160 KiB
  buffer) the final `c[-1] = '\n'` wrote one byte before the buffer (the output itself was still
  accepted, ending in a space). No official case has such a count. Fixed by flushing before a block.
- Untested: the real judge; THP `never`; Intel judge hardware.

## Unsuccessful or neutral

- Input: guarded mapping (zero page before the data) for look-behind parsing; read() instead of mmap
  (calibrated slower); MAP_POPULATE (slower).
- Parser: tail-window and 8-token variants of flat; 8 lockstep streams (spills in `ms`, and in
  `ms3` it was slower on AMD); 16 and 32 KiB chunks (per-chunk overhead).
- Formatter: more than two interleaved `blocks` (equal); `blocks3<2>` end to end; output buffers
  above 160 KiB; mmap-based output (calibrated 226–237 ms vs 130 ms for write()).
